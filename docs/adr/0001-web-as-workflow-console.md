# ADR 0001: Web 保持为视觉工作流操作台，后端逐步抽象工作流内核

## 状态

已采纳

## 背景

当前产品已经具备模板换产品、局部重绘、文字修改、继续优化、历史成图、素材库、回收站和分支路径等能力。

这些能力本质上不是孤立工具，而是电商视觉生产工作流中的不同节点。用户也明确认可「积木式模块搭建」方向，并认为扣子工作流适合作为后端封装，同时前端仍然适合用 Web 页面展示和使用。

## 决策

产品 2.0 不把 Web 替换为扣子工作流，也不继续把 Web 做成零散工具集合。

采用以下分层：

- Web：视觉工作流操作台，负责图片密集操作、框选、人审、资产管理和运行路径展示。
- 工作流内核：负责工作流定义、运行状态、步骤记录、父子关系和分支路径。
- 扣子 / Agent：负责 AI 节点封装、自然语言入口、自动调度、条件分支和生产总结。

短期先沉淀固定工作流模板，不做通用拖拽式工作流编辑器。

## 取舍

### 方案 A：继续堆 Web 工具页面

优点：开发快，延续当前结构。

缺点：导航会越来越复杂，功能之间割裂，历史路径和自动化难以沉淀。

### 方案 B：完全迁移到扣子工作流

优点：天然支持 AI 编排和自动化。

缺点：不适合高密度图片浏览、区域框选、批量人审和素材库管理。

### 方案 C：Web 操作台 + 工作流内核 + 扣子编排层

优点：保留 Web 在视觉操作上的优势，同时为自动化和 Agent 编排打基础。

缺点：需要逐步引入工作流数据模型，短期架构复杂度上升。

最终选择方案 C。

## 影响

- 后续新增能力优先判断它属于输入、AI 处理、人审判断、输出还是资产管理节点。
- 左侧导航不再按工具无限扩展，而应向工作流模板、历史运行、素材库等概念收敛。
- 生成结果需要逐步补充 workflow/run/step/parentAsset 等关系字段。
- 扣子工作流接入应从节点封装开始，而不是直接替换 Web 前端。

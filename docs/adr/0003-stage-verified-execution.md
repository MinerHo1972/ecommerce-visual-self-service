# ADR 0003: 复杂切片采用分阶段可失败验证流程

## 状态

已采纳

## 背景

电商视觉自助台已经从单点生图工具升级为「工作流操作台」。后续 Slice 7「扣子工作流接入预研」和 VLM 质检日志设计都会跨越产品判断、数据结构、API 边界、前端展示、线上部署与长期记忆。

这类任务如果直接一口气推进，容易出现三类问题：

- 前期假设没写清，后面实现时才发现方向偏了。
- 验证只停留在「看起来对」，没有能失败的检查。
- 多 session 延续时，只知道大概做过什么，不知道哪些已经验证、哪些只是推断。

`fable-mode` 的价值不是提供新功能，而是提供复杂任务执行纪律：先做 stage map，独立任务可并行分派，每阶段用可失败检查验收，交付前做怀疑式自审。

## 决策

从 Slice 7 开始，复杂切片默认采用「分阶段可失败验证」流程。

每个复杂切片开工前必须先写 stage map：

```text
Stage 1: [阶段名] → [可检查产物]
Stage 2: [阶段名] → [可检查产物]
Stage 3: [阶段名] → [可检查产物]
```

每个 stage 必须满足：

- 有明确产物，不能只有「理解一下」「优化一下」。
- 有至少一个可失败验证；如果确实无法验证，必须标记为未验证。
- 如果后续修复推翻了前序假设，需要回到对应 stage 重新验证。

交付时必须列明：

- 已验证：真实跑过或真实读过的检查。
- 未验证：因为成本、权限、数据不足或风险暂未验证的部分。
- 下一步风险：最可能影响后续切片的开放问题。

## 适用范围

适用：

- 跨多文件的功能开发。
- 跨产品、技术、数据、部署的切片。
- 多来源调研后形成方案或 ADR。
- 多 session 延续的长期任务。
- 需要子 agent 或后台任务并行处理的工作。

不适用：

- 单文件小修。
- 明确的一步文案调整。
- 一次性问答或轻量判断。
- 不值得写 stage map 的低风险操作。

## 本项目执行模板

### 代码切片

建议 stage：

1. 读取现状 → 确认涉及文件、数据流和旧兼容边界。
2. 写方案或 diff plan → 明确不做什么。
3. 实现最小闭环 → 只改本切片必要范围。
4. 本地验证 → `npx tsc --noEmit`、`git diff --check`、必要 API 或 UI 检查。
5. 部署验证 → GitHub API 推送、ECS 部署、首页健康检查、必要线上接口验证。
6. 状态沉淀 → 更新 `docs/development-status.md` 和必要记忆。

### 方案 / ADR 切片

建议 stage：

1. 读取来源 → PRD、现有代码、外部资料必须实际读取。
2. 列候选 → 至少比较可行方案与不选方案。
3. 写决策 → 明确短期方案、长期迁移路径和风险。
4. 自审验证 → 检查是否覆盖输入输出、失败重试、人审、兼容旧数据。

### 调研切片

建议 stage：

1. 收集来源 → 每个关键事实来自实际读取的来源。
2. 提取证据 → 区分事实、推断和建议。
3. 映射到项目 → 明确落到产品流程、技术方案、数据结构还是仅作参考。
4. 输出结论 → 标注无法确认的信息和下一步验证方式。

## Slice 7 前置应用

Slice 7 不直接接入扣子工作流，先用本流程做预研：

1. Stage 1: 读取现状 → 自助工作台、生成 API、Grsai 服务、运行路径 API、ADR 0001/0002。
2. Stage 2: 节点评估 → 比较模板换产品、局部重绘、文字修改、自动质检。
3. Stage 3: 方案草案 → 选出第一个适合封装为扣子工作流的节点。
4. Stage 4: 可失败验证 → 检查输入输出边界、失败重试、人审回传、旧链路兼容是否都被覆盖。

通过后再决定是否进入真实接入切片。

## 验收标准

- `docs/development-status.md` 能索引本 ADR。
- 后续复杂切片交付时能看到 stage map、已验证、未验证和风险。
- Slice 7 预研先产出方案或 ADR，不直接改线上生成链路。

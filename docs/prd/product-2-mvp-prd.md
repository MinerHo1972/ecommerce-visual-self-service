# PRD：电商视觉工作流操作台 2.0 MVP

## 1. 背景与问题

### 当前问题

当前产品已经具备产品图输入、模板图输入、区域框选、候选生成、反馈标签、局部重绘、继续优化、历史成图、产品库、模板库、回收站和分支路径等能力。

但这些能力仍以独立功能点的方式存在，用户容易把它理解成一个工具集合，而不是一条连续的视觉生产流程。

具体问题：

- 新能力如果继续以一级页面方式增加，左侧导航会越来越臃肿。
- 「模板换产品」「局部重绘」「继续优化」「带回工作台」「分支路径」之间的关系还不够清晰。
- 历史成图仍偏图片列表，不够像一次次工作流运行记录。
- 当前分支路径能解释父图、同批候选、子分支，但还没有升级为完整「运行路径」。
- 数据层缺少明确的 workflow/run/step 概念，后续接扣子工作流或自动化调度会缺基础。

### 影响对象

- 电商运营：希望快速生产、筛选和复用商品视觉图。
- 视觉运营：希望看清楚每张图的生成来源和优化路径。
- 后续 Agent / 扣子工作流：需要结构化流程数据，才能自动发起、追踪和总结任务。

### 为什么现在要做

产品已经完成 1.0 主链路，继续堆功能会导致复杂度上升。现在需要先统一产品语义和数据基础，把后续能力纳入工作流框架，避免越做越散。

## 2. 目标与非目标

### 目标

- 将产品 2.0 的前台体验从「工具集合」升级为「工作流操作台」。
- 将现有「自助工作台」定义为首个默认工作流模板：商品图套模板。
- 将「分支路径」逐步升级为「运行路径」概念。
- 把「继续优化」「局部重绘」「带回工作台」统一表达为基于图片的「下一步动作」。
- 为新生成数据补充 workflow/run/step/parentAsset 关系字段或等价结构。
- 保留 Web 作为视觉操作、人审和素材管理主入口。
- 为后续接入扣子工作流打好边界，而不是本阶段直接全量接入。

### 非目标

- 不做通用拖拽式工作流编辑器。
- 不把 Web 前端替换成扣子工作流页面。
- 不一次性重构全部历史数据。
- 不本阶段实现复杂多用户权限、公共区/私人区。
- 不本阶段实现完整成品库，除非作为后续概念预留。
- 不本阶段自动触发真实批量生成，避免成本和稳定性风险。

## 3. 用户与场景

### 目标用户

- 电商运营
- 视觉运营
- 商品上新负责人
- 后续可扩展到 Agent 辅助运营

### 高频场景

1. 用户选择一个产品图和一个模板图，生成多张候选图。
2. 用户从候选图中判断可用或不可用，并打反馈标签。
3. 用户对某张图继续优化或局部重绘。
4. 用户从历史成图中带回一张图，继续做下一轮。
5. 用户查看某张图的来源、同批候选和子分支。
6. 用户下载、入库或移入回收站。

### 边界场景

- 历史旧数据没有 workflow 字段时，仍能按现有 jobId、parentImageId、tags 兼容展示。
- 生成失败、超时或图片缺失时，运行路径中应能显示失败状态，而不是静默消失。
- 用户不需要理解底层扣子工作流，只需要看到清晰步骤和下一步动作。

## 4. 用户流程

### 4.1 商品图套模板流程

1. 用户进入「自助工作台」。
2. 页面展示当前工作流名称：商品图套模板。
3. 用户选择或上传产品图。
4. 用户选择或上传模板图。
5. 用户框选商品放置区域。
6. 用户设置抽卡次数和补充指令。
7. 用户点击生成。
8. 系统创建一次工作流运行，并进入 AI 处理节点。
9. 系统返回候选图。
10. 用户对候选图打反馈标签。
11. 用户选择下一步动作：下载、继续优化、局部重绘、移入回收站或查看运行路径。

### 4.2 历史成图继续优化流程

1. 用户进入历史成图或历史运行。
2. 用户选择一张历史图片。
3. 用户点击「带回工作台」或「继续优化」。
4. 系统将该图片作为父图或产品图输入带入自助工作台。
5. 页面提示当前图片来自历史运行。
6. 用户补充新要求并生成。
7. 新结果作为该历史图片的子分支展示。

### 4.3 局部重绘流程

1. 用户在候选图或历史成图中选择「局部重绘」。
2. 用户框选需要修复的区域。
3. 用户输入修复说明，可选择参考图。
4. 系统创建新的工作流步骤或子运行。
5. 系统返回局部重绘结果。
6. 用户人审并决定下一步。

### 4.4 查看运行路径流程

1. 用户点击图片上的「运行路径」或当前「分支路径」。
2. 系统展示父图、当前图、同批候选、子分支。
3. 对新数据，系统优先按 workflow/run/step 关系展示。
4. 对旧数据，系统按兼容逻辑展示。
5. 用户可以从路径中任意图片继续带回工作台、下载或查看详情。

## 5. 功能需求

### 5.1 工作流语义统一

描述：前台文案从工具语言逐步切换为工作流语言。

规则：

- 「自助工作台」展示当前工作流模板名称。
- 「分支路径」可逐步更名为「运行路径」。
- 「继续优化」「局部重绘」「下载」「移入回收站」归类为「下一步动作」。
- 不再恢复「最终图」前台概念，继续使用反馈标签表达质量判断。

状态：MVP 必做。

异常：旧页面或旧数据不强制修改，只保证新主链路一致。

### 5.2 工作流模板入口

描述：新增或预留「工作流模板」入口，展示固定高频流程。

首批模板：

- 商品图套模板
- 历史成图继续优化
- 局部重绘修瑕疵
- 批量上新图生产
- 文字修改与模板复用

规则：

- MVP 阶段可先展示模板卡片和说明，不要求全部可执行。
- 已可执行模板应能跳转到对应工作台或带入参数。
- 未接入模板应标记「即将接入」，避免用户误以为已经可用。

状态：MVP 建议做轻量版本。

### 5.3 自助工作台工作流化

描述：将现有自助工作台明确为「商品图套模板」工作流。

规则：

- 页面顶部显示工作流名称、当前步骤和简短说明。
- 输入区明确区分产品图、模板图、参考图、补充指令。
- 候选结果区保留反馈标签和下一步动作。
- 生成后记录 workflow 相关关系字段或兼容结构。

状态：MVP 必做。

### 5.4 历史成图升级为运行视角

描述：历史成图继续保留图片列表能力，但逐步增加运行维度。

规则：

- 图片卡片显示所属工作流或兼容来源。
- 图片详情或抽屉中显示运行路径。
- 支持按反馈标签、工作流类型、时间筛选的扩展空间。
- 旧数据无工作流名称时显示兼容文案，例如「历史生成」。

状态：MVP 部分做。

### 5.5 运行路径

描述：运行路径用于替代纯图片谱系，让用户理解一张图的生产过程。

规则：

- 至少展示父图、当前图、同批候选、子分支。
- 新数据优先使用 workflowRunId、stepRunId、parentAssetId。
- 旧数据继续使用现有 jobId、inputs_snapshot.parentImageId、tags 兼容。
- 路径中的图片支持下载、带回工作台、继续下一步。

状态：MVP 必做概念和基础展示，不要求复杂树状图。

### 5.6 工作流数据基础

描述：为新生成链路补充工作流运行关系。

规则：

- 每次生成应有工作流运行标识。
- 每个 AI 处理步骤应有步骤运行标识。
- 每张生成图应能关联到运行、步骤和父图。
- 不强制回填历史旧数据。
- 数据字段命名需在开发设计阶段结合现有 schema 再确认。

状态：MVP 必做，但可以先以最小字段落地。

### 5.7 扣子工作流边界预留

描述：本阶段不直接全量接入扣子工作流，但要让接口边界未来可替换。

规则：

- AI 处理节点调用应逐步从页面逻辑中抽离到服务层。
- Web 调用的是「运行某个工作流/步骤」，而不是直接关心底层 AI 服务细节。
- 后续可将某个步骤替换为扣子工作流调用。

状态：MVP 预留，不强制接入。

## 6. 业务规则

- 规则 1：Web 仍是主入口，所有需要看图、框选、人审、下载的操作优先在 Web 完成。
- 规则 2：新增能力先判断属于输入、AI 处理、人审判断、输出还是资产管理节点，不默认新增一级页面。
- 规则 3：「最终图」前台概念不恢复；如果未来需要交付态，应重新设计为「成品图」或「入成品库」。
- 规则 4：工作流模板先固定，不做自由拖拽。
- 规则 5：旧历史数据必须兼容展示，不能因为没有 workflow 字段而不可用。
- 规则 6：生成图必须继续先落 OSS 再入库。
- 规则 7：删除仍走回收站，永久删除必须保持管理员确认机制。
- 规则 8：真实生成、局部重绘、文字修改仍不在部署验证中自动触发。

## 7. 数据对象与字段影响

| 对象 | 字段 | 类型 | 必填 | 来源 | 说明 |
| --- | --- | --- | --- | --- | --- |
| WorkflowDefinition | id | string | 是 | 系统生成 | 工作流模板标识 |
| WorkflowDefinition | name | string | 是 | 系统配置 | 例如商品图套模板 |
| WorkflowDefinition | description | string | 否 | 系统配置 | 模板说明 |
| WorkflowDefinition | inputSchema | json | 否 | 系统配置 | 输入结构定义 |
| WorkflowDefinition | steps | json | 是 | 系统配置 | 节点定义 |
| WorkflowRun | id | string | 是 | 系统生成 | 一次运行标识 |
| WorkflowRun | workflowDefinitionId | string | 是 | 系统生成 | 关联工作流模板 |
| WorkflowRun | status | enum | 是 | 系统更新 | pending/running/succeeded/failed/canceled |
| WorkflowRun | inputSnapshot | json | 否 | 用户输入 | 本次运行输入快照 |
| WorkflowStepRun | id | string | 是 | 系统生成 | 步骤运行标识 |
| WorkflowStepRun | workflowRunId | string | 是 | 系统生成 | 所属工作流运行 |
| WorkflowStepRun | stepId | string | 是 | 系统配置 | 所属步骤 |
| WorkflowStepRun | type | enum | 是 | 系统配置 | input/ai/human_review/condition/output |
| WorkflowStepRun | status | enum | 是 | 系统更新 | pending/running/succeeded/failed/canceled |
| WorkflowStepRun | parentStepRunId | string | 否 | 系统生成 | 上一步或父步骤 |
| GeneratedAsset | workflowRunId | string | 否 | 系统生成 | 新数据建议必填，旧数据可为空 |
| GeneratedAsset | stepRunId | string | 否 | 系统生成 | 关联生成步骤 |
| GeneratedAsset | parentAssetId | number/string | 否 | 用户动作/系统生成 | 父图关系 |
| GeneratedAsset | feedbackTags | string[] | 否 | 用户输入 | 人审反馈标签 |

说明：字段名为 PRD 草案，最终落地需结合现有数据库表和 repository 命名确认。

## 8. API / 系统边界影响

| 接口/模块 | 用途 | 输入 | 输出 | 错误/边界 |
| --- | --- | --- | --- | --- |
| 工作流模板查询 | 获取固定工作流模板 | 无或模板类型 | 模板列表/详情 | 未接入模板需标记不可执行 |
| 创建工作流运行 | 发起一次工作流 | workflowDefinitionId、inputSnapshot | workflowRunId、初始状态 | 输入缺失、模板不可用 |
| 执行工作流步骤 | 执行 AI 或人审后续步骤 | workflowRunId、stepId、输入 | stepRunId、状态、输出 | AI 超时、失败、取消 |
| 生成图保存 | 保存生成结果 | stepRunId、图片 URL、父图 | generatedImage/asset | OSS 缺失不得入库 |
| 运行路径查询 | 查询图片或运行的路径 | imageId 或 workflowRunId | 父图、当前图、同批候选、子分支 | 旧数据走兼容逻辑 |
| 历史成图列表 | 展示历史图片与运行信息 | 筛选条件 | 图片列表 | 无 workflow 字段时展示兼容来源 |

## 9. 验收标准

- [ ] 用户进入自助工作台时，能明确看到当前工作流是「商品图套模板」。
- [ ] 候选图操作能统一归类为下一步动作，不再出现「最终图」概念。
- [ ] 历史成图中的路径入口能用「运行路径」或等价文案解释父图、当前图、同批候选、子分支。
- [ ] 新生成图片能记录与工作流运行相关的最小关系字段。
- [ ] 旧历史图片仍能正常加载、下载、移入回收站、带回工作台。
- [ ] 工作流模板入口能区分「已可用」和「即将接入」。
- [ ] 未接入扣子工作流时，现有生成链路不受影响。
- [ ] TypeScript 检查通过。
- [ ] 部署后线上首页健康检查返回 200。

## 10. 测试决策

### 关键行为

- 自助工作台生成流程不回退。
- 历史成图操作不回退。
- 分支/运行路径兼容旧数据。
- 新数据能建立 workflow/run/step/asset 关系。
- 未接入模板不会误导用户点击执行。

### 建议测试层级

- 单元测试：数据映射、运行路径组装、旧数据兼容逻辑。
- API 测试：创建运行、查询路径、保存生成图。
- UI 手工验收：自助工作台、历史成图、工作流模板入口。
- 部署验收：`npx tsc --noEmit`、`git diff --check`、ECS 构建和健康检查。

### 不测试实现细节

- 不测试 CSS 内部类名。
- 不自动触发真实 GRSai 生成作为常规部署测试。
- 不在 MVP 阶段测试通用拖拽工作流编辑能力。

## 11. 待确认问题

- 「工作流模板」是否立即作为一级导航，还是先放在自助工作台内？
- 「历史成图」是否改名为「历史运行」，还是保留现名并增加运行维度？
- 第一个接入扣子工作流的节点应该是模板换产品、局部重绘、文字修改，还是自动质检？
- 是否需要在 MVP 引入「成品图 / 成品库」概念？
- 「可用」标签是否应触发入库建议或成品建议？
- 批量上新图生产是否进入 2.0 第一阶段，还是放到第二阶段？
- 运行路径 MVP 用卡片式即可，还是需要树状图？

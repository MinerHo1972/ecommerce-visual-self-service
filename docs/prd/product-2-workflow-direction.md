# 电商视觉工作流操作台：产品 2.0 方向文档

## 1. 背景

当前产品已经从最早的单点图片生成能力，逐步演进出一组完整的电商视觉生产能力：产品图输入、模板图输入、区域框选、模板换产品、生图候选、反馈标签、局部重绘、继续优化、历史成图、产品库、模板库、回收站、分支路径等。

这些能力表面上是不同按钮、页面和操作入口，但底层逻辑越来越清晰：用户定义输入，系统进入 AI 处理节点，生成候选结果，再由人判断是否进入下一轮优化、局部修复、入库、下载或废弃。

这意味着产品不应继续沿着「不断新增工具页面」的方式演进，而应该进入 2.0：从「电商视觉自助台」升级为「电商视觉工作流操作台」。

产品 2.0 的核心不是做更多零散工具，而是把各种视觉生产能力抽象为积木式模块，让用户可以基于固定工作流完成高频任务，未来再逐步组合成更复杂的半自动或全自动工作流。

## 2. 产品 2.0 定位

### 2.1 1.0 定位

电商视觉自助台：用户在 Web 页面中完成图片生成、优化和素材管理。

### 2.2 2.0 定位

电商视觉工作流操作台：面向电商运营和视觉生产场景，将素材输入、AI 处理、人审判断、分支继续、资产沉淀和导出串成可复用工作流。

### 2.3 一句话定义

一个面向电商视觉生产的 AI 工作流操作台：Web 负责看图、选图、框选、人审和资产管理；后端工作流负责 AI 节点编排、运行状态、分支路径和自动化调度。

## 3. 为什么要升级到 2.0

### 3.1 当前产品已经出现工作流特征

现有操作已经不是单次生成，而是连续链路：

```text
选择产品图 → 选择模板图 → 框选区域 → 生成候选 → 人审反馈 → 继续优化 / 局部重绘 / 下载 / 入库
```

历史成图、分支路径、带回工作台，本质上都是在支持「从任意节点继续下一轮」。

### 3.2 继续堆工具会让产品变复杂

如果每新增一种能力就新增一个一级页面，左侧导航会越来越臃肿，用户也会越来越难判断应该从哪里开始。

模板换产品、局部重绘、文字修改、批量套模板、历史图继续优化、自动质检和成品入库，不应该是彼此割裂的工具，而应该是一个工作流里的不同节点。

### 3.3 扣子工作流适合承载后端封装

扣子工作流适合做 AI 工作流、节点编排、条件分支和 Agent 调度。

但它不适合完全替代 Web，因为当前产品有大量图片密集、人审密集、区域框选和素材管理操作。

因此更合理的方向不是「Web 或扣子二选一」，而是：

```text
Web = 专业视觉操作台
工作流后端 = 业务编排与运行状态
扣子 / Agent = AI 节点封装、自动调度和自然语言入口
```

## 4. 产品 2.0 核心原则

1. 不再把工具当一级入口堆叠，而是把工具抽象成工作流节点。
2. 不一上来做通用拖拽编辑器，先沉淀固定高频工作流模板。
3. Web 继续作为核心入口，负责图片密集型操作和人工判断。
4. 扣子工作流作为后端封装和智能编排层，不替代 Web。
5. 所有生成结果都要能追踪来源、输入、父图、同批候选和子分支。
6. 人审不是临时过渡，而是电商视觉生产中的关键产品能力。
7. 工作流数据模型先行，UI 逐步升级，不推倒重来。

## 5. 产品架构

### 5.1 总体分层

```text
Web 操作台
  - 素材选择
  - 参数填写
  - 区域框选
  - 结果预览
  - 人审反馈
  - 分支路径查看
  - 下载 / 入库 / 回收

工作流内核
  - WorkflowDefinition
  - WorkflowRun
  - WorkflowStepRun
  - HumanReviewPoint
  - OutputAsset

AI / 扣子工作流层
  - 模板换产品节点
  - 局部重绘节点
  - 文字修改节点
  - 自动质检节点
  - 条件分支节点
  - 批量生成节点
  - 定时 / Agent 调度
```

### 5.2 Web 操作台职责

Web 负责用户直接操作和判断的部分：

- 上传或选择产品图、模板图、参考图。
- 框选产品区域或局部重绘区域。
- 设置抽卡次数、补充指令、反馈标签。
- 浏览高密度候选图。
- 对比同批候选和分支路径。
- 下载、入库、回收、继续优化。

Web 不应该承担：

- 所有 AI 编排逻辑。
- 复杂条件分支执行。
- 长任务调度。
- 通用工作流编辑器能力。

### 5.3 工作流内核职责

工作流内核负责把一次视觉生产过程结构化：定义当前跑的是哪个工作流，记录每一步输入输出，记录每张图属于哪个步骤，记录父图、同批候选、子分支，并支持从任意节点继续下一步。

### 5.4 扣子 / Agent 职责

扣子或 Agent 适合做智能编排层：把自然语言需求转成工作流参数，根据任务选择合适工作流模板，调用 AI 节点，做条件分支与自动重试，定时触发批量任务，生成生产报告或运营总结。

## 6. 积木模块抽象

### 6.1 输入模块

- 产品图输入：上传、产品库选择、历史成图带回。
- 模板图输入：模板库选择、上传、历史图复用。
- 参考图输入：用于风格参考、局部修复或相似构图。
- 文本约束输入：产品约束、模板约束、本轮补充指令。
- 区域输入：产品放置区域、局部重绘区域。

### 6.2 AI 处理模块

- 模板换产品。
- 局部重绘。
- 文字修改。
- 继续优化。
- 批量套模板。
- 图像裁切 / 压缩 / 格式转换。
- 自动质检。

### 6.3 判断模块

- 人工反馈：可用、产品不对、模板跑偏、文案变了、自定义标签。
- 自动判断：尺寸是否合规、是否有生成失败、是否缺少主体、是否疑似文案污染。
- 条件分支：不同反馈进入不同下一步。

### 6.4 输出模块

- 下载。
- 入历史成图。
- 入产品库。
- 入模板库。
- 入成品库。
- 移入回收站。
- 同步外部系统。

## 7. 首批工作流模板

### 7.1 商品图套模板

目标：把一个产品图套入一个模板图，生成多张候选图。

流程：

```text
选择产品图 → 选择模板图 → 框选商品区域 → 填约束 → 生成候选 → 人审反馈 → 下载 / 继续优化 / 局部重绘
```

当前「自助工作台」就是这个工作流的第一版。

### 7.2 历史成图继续优化

目标：基于一张历史成图继续生成新分支。

流程：

```text
选择历史成图 → 带回工作台 → 作为父图 → 选择优化方向 → 生成子分支 → 人审
```

### 7.3 局部重绘修瑕疵

目标：只修复一张图的局部问题。

流程：

```text
选择图片 → 框选问题区域 → 输入修复说明 → 可选参考图 → 局部重绘 → 人审
```

### 7.4 批量上新图生产

目标：多个产品图批量套入一个或多个模板，生成上新素材。

流程：

```text
选择产品集合 → 选择模板集合 → 设置生成数量 → 批量生成 → 批量人审 → 下载 / 入库
```

### 7.5 文字修改与模板复用

目标：保留模板结构，仅修改局部文案，形成新模板或新成图。

流程：

```text
选择模板 → 识别文字层 / 输入修改要求 → 生成新版本 → 人审 → 保存为新模板 / 继续使用
```

## 8. 信息架构建议

### 8.1 左侧导航从工具列表升级为工作区

建议方向：

- 自助工作台
- 工作流模板
- 历史运行
- 素材库
- 回收站
- 设置

### 8.2 自助工作台

默认进入最高频工作流「商品图套模板」。

页面结构：

- 左侧：输入区。
- 中间：当前工作流步骤。
- 右侧或底部：候选结果与人审操作。
- 抽屉：分支路径 / 运行路径。

### 8.3 工作流模板

展示固定高频模板，而不是一开始做自由拖拽。

示例：商品图套模板、历史成图继续优化、局部重绘修瑕疵、批量上新图生产、文字修改与模板复用。

### 8.4 历史运行

历史成图未来不只是图片列表，而是工作流运行记录。

需要展示运行时间、工作流名称、输入素材、生成候选、反馈标签、子分支数量和可继续操作。

## 9. 分支路径升级方向

### 9.1 当前概念

- 父图：上一轮作为输入的图。
- 当前图：用户正在查看的图。
- 同批候选：同一次生成任务产生的其他候选图。
- 子分支：基于当前图继续优化产生的新结果。

### 9.2 2.0 目标概念

分支路径升级为「工作流运行路径」。

示例：

```text
WorkflowRun
  Step 1: 输入素材
  Step 2: 模板换产品
    Candidate A: 可用
    Candidate B: 产品不对
    Candidate C: 模板跑偏
  Step 3: 基于 Candidate A 局部重绘
  Step 4: 下载 / 入库
```

### 9.3 用户价值

- 看清楚一张图怎么来的。
- 找回某一轮里的其他候选。
- 从任意节点继续分支。
- 比较不同优化路径的效果。
- 为批量复盘和自动化优化提供数据基础。

## 10. 数据模型方向

### 10.1 WorkflowDefinition

定义一个可复用工作流模板。

字段草案：

```text
id
name
description
inputSchema
steps
humanReviewPoints
outputRules
createdAt
updatedAt
```

### 10.2 WorkflowRun

记录一次工作流运行。

字段草案：

```text
id
workflowDefinitionId
status
currentStepId
inputSnapshot
createdAt
updatedAt
```

### 10.3 WorkflowStepRun

记录一次具体步骤执行。

字段草案：

```text
id
workflowRunId
stepId
type
status
inputSnapshot
outputSnapshot
parentStepRunId
createdAt
updatedAt
```

### 10.4 GeneratedAsset

记录生成资产与工作流关系。

字段草案：

```text
id
workflowRunId
stepRunId
parentAssetId
url
thumbnailUrl
feedbackTags
status
createdAt
updatedAt
```

### 10.5 兼容策略

短期不迁移历史数据，先对新生成数据补充工作流字段。

旧数据继续通过现有 `jobId`、`inputs_snapshot.parentImageId`、tags 等字段兼容展示。

## 11. MVP 范围

### 11.1 本阶段要做

- 明确产品 2.0 命名：电商视觉工作流操作台。
- 将现有「自助工作台」定义为第一个工作流模板：商品图套模板。
- 将「分支路径」逐步升级为「运行路径」。
- 在数据层开始记录 `workflowRunId`、`stepRunId`、`parentAssetId`。
- 在 UI 上把「继续优化」「局部重绘」「带回工作台」统一表达为「下一步动作」。
- 保留 Web 页面作为人审和视觉操作台。

### 11.2 本阶段不做

- 不做通用拖拽式工作流编辑器。
- 不一次性迁移到扣子工作流。
- 不推倒现有 Web 重写。
- 不做复杂权限系统。
- 不做多用户公共区/私人区，除非后续明确进入团队协作阶段。

## 12. 演进路线

### 12.1 第一阶段：产品语义统一

- 页面标题、按钮、提示语统一成工作流语言。
- 自助工作台展示当前工作流名称。
- 历史成图增加运行路径概念。
- 常用操作从工具入口改成工作流入口。

### 12.2 第二阶段：数据模型补强

- 增加 workflow/run/step 概念。
- 对新生成图记录 workflow 相关字段。
- 旧数据兼容保留。
- 分支路径逐步基于 workflow 数据展示。

### 12.3 第三阶段：工作流模板库

- 展示固定工作流模板。
- 用户选择模板后进入对应输入表单。
- 不开放自由拖拽，只开放参数配置。
- 支持从历史运行复制为新运行。

### 12.4 第四阶段：接入扣子工作流

- 将 AI 处理节点逐步封装到扣子工作流或后端工作流。
- Web 调用工作流运行接口。
- Agent 可以根据自然语言发起工作流。
- 扣子工作流负责复杂节点和自动化编排。

### 12.5 第五阶段：半自动 / 全自动生产

- 批量任务。
- 自动质检。
- 自动重试。
- 定期汇总。
- 与外部电商平台或飞书协作链路打通。

## 13. 后续待讨论问题

- 「工作流模板」是否作为一级导航，还是放在自助工作台内部？
- 「历史成图」是改名为「历史运行」，还是保留图片视角并增加运行维度？
- 扣子工作流先接哪一个节点最合适：模板换产品、局部重绘、文字修改，还是自动质检？
- 是否需要一个「成品库」区别于历史成图和产品库？
- 「可用」标签是否应触发入成品库建议？
- 批量生产什么时候进入 MVP？
- 运行路径先做卡片式，还是直接做树状图？
- 哪些流程允许 Agent 自动推进，哪些必须人工确认？

## 14. 当前结论

产品 2.0 方向确认：继续保留 Web，但将其定位从「自助工具集合」升级为「工作流操作台」。

Web 专注视觉操作、人审和资产管理；后端逐步抽象工作流内核；扣子工作流和 Agent 作为 AI 节点封装、自动化编排和自然语言入口。

短期先做产品语义、数据模型和固定工作流模板，不做通用拖拽编辑器，不推倒重来。
